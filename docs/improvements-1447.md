## 사용법

- **체크리스트 의존성:** 마스터가 `checklist` 도구로 단계에 `id`, 담당자(`owner`), 선행(`dependsOn`), 연결 협의(`consultIds`)를 적는다. 목표·계획 패널에 담당자와 "대기 · 선행 미완료: …" 표시가 나온다. 연결 협의를 누르면 데스크톱은 해당 협의 기록으로 이동하고, 원격 웹은 같은 화면의 협의 카드로 스크롤해 포커스하며 접힌 구역도 연다. 원격 화면에 카드가 없는 협의는 비활성이다.
- **구조화 리뷰:** review로 배정된 작업자가 `report_review`로 판정·지적 사항·테스트 결과를 제출한다. 협의 카드에 판정(통과·수정 요청·판단 보류), 심각도별 지적, 테스트 상태가 나온다. 채팅 상단 합계줄은 리뷰 건수, 판정별 개수, 진행 중·실행 미완료·구조화 결과 없음 개수를 보여 준다. 보고 없이 끝난 리뷰는 "구조화 결과 없음"이며 통과로 세지 않는다. 오류·중지·한도로 끝난 리뷰의 판정은 합계에 넣지 않는다.
- **실행 통계:** 채팅 상단의 막대그래프 아이콘(실행 통계)을 누른다. 채팅 전체, 역할별, 협의별로 기록 구간, 도구 실행, 승인 대기, 상태, 기록 수를 표로 보여 준다. 기록 구간은 첫 기록부터 마지막 기록까지이며 유휴 시간을 포함한다. 도구 실행과 승인 대기는 겹칠 수 있어 더하지 않는다. 결과를 받지 못한 도구 호출은 '결과 미확인'으로 표시하며, 아직 실행 중인 호출과 턴이 끝날 때까지 결과가 없던 호출을 함께 센다. 토큰·비용·모델 추론 시간은 계산하지 않는다.
- **대화 분기:** 메인 타임라인의 사용자 메시지나 마스터의 저장된 일반 답변에 마우스를 올리거나 포커스하면 나오는 "분기" 버튼을 누른다. 작업자 답변, 협의 화면, 그룹 발언(`room_message`)에는 버튼이 없다. 범위('처음부터 이 메시지까지' 또는 '이 메시지부터 끝까지')와 첨부 포함 여부를 고르면 새 채팅이 생긴다. 새 채팅 상단에 원본 제목·번호와 "원본 열기"가 표시된다. 원본이 삭제됐으면 "원본 없음(삭제됨)"으로 표시된다. 분기한 대화 원문은 접힌 읽기 전용 카드로 들어가며 채팅 검색으로 찾을 수 있다. 원격 웹도 같은 흐름을 제공한다.
- **재개 정보:** 따로 조작하지 않는다. 앱 종료·크래시로 끊긴 협의를 다음 실행에서 이어 갈 때 작업자와 마스터에게 자동으로 전달된다. 이전 버전 기록이라 실행 중이던 지시를 확정할 수 없으면 자동으로 이어 가지 않고 안내를 남긴 뒤 대기 상태가 되며, 새 지시로 계속할 수 있다.

## 1. 작업 의존성

- `PlanStep`에 선택 필드 `id`, `owner`, `dependsOn`, `consultIds`를 추가했다. `{title, status}`만 있는 기존 목록은 그대로 유효하다.
- `src/shared/plan-steps.ts`의 `validatePlanSteps`가 중복 id, 없는 선행, 자기참조, 순환을 거부한다. `planStepBlockers`는 완료되지 않은 직접 선행을 돌려준다.
- `checklist` 도구는 시작 가능·선행 대기·연결 협의 미완료를 결과로 돌려준다. 이 채팅에 없는 협의 id는 거부한다.
- 앱은 이 정보로 작업을 배정하거나 단계를 완료 처리하지 않는다. 담당자는 표시용 닉네임이다.

## 2. 구조화 리뷰

- 작업자 전용 도구 `report_review`를 추가했다. 브리지가 호출자 역할에 묶여 있어 현재 실행 중인 자신의 review 협의에만 저장되며, 인수로 협의 id를 지정할 수 없다.
- `consults.review_json`에 저장하고 `review_result` 이벤트를 협의 노드에 남긴다. 저장은 `status = 'running'`인 협의에만 적용되어 끝난 협의는 바꿀 수 없다.
- 형식이 잘못된 보고는 부분 저장하지 않고 제출자에게 오류를 돌려준다(`src/shared/review-result.ts`).
- 유효한 보고만 제출하고 자유문장이나 파일 없이 정상 종료해도 협의는 완료(done)이며, 요약과 `consult_end`에 판정과 요약문이 남는다. 실행 실패·중단·사용자 중지는 보고가 있어도 각각 error·stopped를 유지하고, 제출된 보고는 보존한다.
- 보고가 없으면 협의 결과에 미제출을 표시하고 통과로 간주하지 않는다. 새 승인 게이트, review 읽기 전용 강제, 파일·patch 자동 적용은 없다.

## 3. 실행 통계

- `src/shared/run-stats.ts`는 이벤트 기록만으로 노드별 기록 구간, 도구 실행·승인 대기 구간의 합집합, 결과 없는 호출, 대기 중 승인, 실패한 도구·턴을 계산한다. DB나 IPC를 바꾸지 않는다.
- 같은 id로 다시 받은 이벤트는 한 번만 센다. 도구 id는 노드·역할 단위로 짝지으며, 턴 종료는 자기 대화의 호출만 닫는다. 앱이 자동 승인한 요청은 대기 구간이 되지 않는다. 사용자 중지는 실패로 세지 않는다.
- 결과 없이 턴이 끝난 호출은 턴 종료 시각까지를 도구 구간으로 넣고 `pendingTools`로 남긴다. 짝이 없는 결과(고아 result)는 시간·실패 어디에도 반영하지 않는다. 이 부분은 지피티 1호 리뷰 지적을 반영한 수정이다.
- 화면의 마스터 행은 마스터 턴이 열려 있을 때만 현재 시각까지 늘어난다. 열림 근거는 대기열이 아닌 새 사용자 지시와 마스터의 `text_delta`·`text`·`tool_call`이다. 작업자만 남아 채팅이 작업 중이어도 끝난 마스터 행은 늘어나지 않는다.

## 4. 재개 정보

- `consults.assignment_json`에 모델, 계정, 첨부 경로, 토의 정보를 저장한다. 로컬 경로가 있어 `Consult` 응답에는 포함하지 않는다.
- 앱 종료·크래시로 끊긴 협의는 다음 실행에서 `interrupted_by = 'app_exit'`로 표시한다. 정상 종료 중에는 협의를 running으로 남겨 같은 경로로 처리한다. 사용자 중지는 표시하지 않는다.
- `src/main/resume-context.ts`가 저장된 기록으로 끊긴 협의, 결과 없는 도구 호출, 추가 지시, 실패, 완료 협의를 12,000자 이내로 만든다. 결정이 필요한 항목을 앞에 두어 길이 제한은 완료 기록부터 잘린다.
- 앱 자체 도구는 목록에서 제외한다. 결과 없는 도구 호출은 턴이 끝났어도 실행 여부를 알 수 없으므로 표시를 유지한다.
- 마스터 계열이 같아도 재개 문구에 포함한다. 작업이나 명령을 자동으로 다시 실행하지 않으며 일시 정지·중지·승인 만료 동작은 바꾸지 않았다.
- 실행 중인 지시를 snapshot(id, 실제 지시 전문, mode, dualInvestigation, 계획·리뷰 제약)으로 DB 설정에 저장한다. 지시 시작, `route_request`, 즉시 전달로 지시 문구가 바뀔 때, 마스터 턴 종료 때 갱신한다. 지시 시작 시점에 저장하므로 `route_request` 전에 끊겨도 정확히 복원하고 mode는 비어 있어 다시 기록해야 한다.
- 재개하면 snapshot의 id·원문·mode·제약을 그대로 복원한다. 모델의 재개 문구 "현재 지시"와 승인 판단기의 지시 원문은 같은 값이다. 이전 일반 지시는 "참고용"으로만 넣는다. 함께 승격된 B1·B2는 합쳐진 실행 원문 그대로 복원한다. 별도 턴이면 그 턴의 원문만 복원한다. 현재 지시에 포함된 추가 지시는 복구 정보의 "추가 지시"에 다시 넣지 않는다.
- snapshot보다 새로운 일반 사용자 메시지가 있으면 snapshot은 끊기기 전 것이므로 쓰지 않는다.
- snapshot이 없는 이전 기록은 하나의 지시와 dispatch가 명확히 대응할 때만 복원한다. 일반 지시는 기존처럼 복원하고, dispatch되지 않은 대기 메시지는 추가 지시 참고로 남긴다. 여러 대기 메시지가 합쳐졌을 수 있거나 dispatch 대상이 없으면 원문을 합성하지 않고 재개를 보류한다. 이 경우 마스터를 시작하지 않으며 지시도 복원하지 않는다.
- 같은 이전 기록에서 복원 대상 지시 뒤에 `delivery: "now"`로 보낸 대기 메시지가 있어도 재개를 보류한다. 즉시 전달은 수락되면 실행 원문에 합쳐지고, 받지 못하면 다음 단계 대기로 바뀌는데, 기록만으로는 어느 쪽인지 알 수 없다. 기존 안내와 함께 idle로 두며 마스터를 시작하지 않는다. `delivery` 필드가 없는 대기 메시지는 필드가 생기기 전(8778ccb 이전) 기록이다. 당시에는 작업 중 메시지가 모두 대기열로만 갔으므로(`busySend = queue`) next로 보고 기존처럼 추가 지시 참고로 남긴다. 더 새로운 일반 지시 C가 있으면 그 이전의 즉시 메시지는 C를 막지 않는다. 유효한 snapshot은 이 검사 전에 그대로 복원되므로 즉시 전달 원문도 정확히 이어진다.
- `/plan-cancel`도 snapshot을 갱신한다. 이전에는 취소 뒤 끊기면 재개할 때 취소한 계획 제약이 되살아났다.
- 계획·리뷰 제약은 snapshot 값을 쓴다. 이전 기록은 현재 지시가 일반 메시지일 때만 `/plan`·`/review`를 판별하며 후속 지시에는 물려주지 않는다.
- 이 수정은 일반 실행의 승인 흐름을 바꾸지 않는다. 판단기의 1500자 절단과 마스터 전환 요약(handover) 정책도 바꾸지 않았다.
- snapshot은 settings 테이블에만 있고 `Consult`·IPC 응답에 포함하지 않는다. 분기한 채팅에 복제되지 않으며 채팅·프로젝트를 지우면 함께 지워진다.

## 7. 사용자 대화 분기

- IPC `chats:fork`, 원격 `POST /api/chats/:id/fork`(`remote:chat-fork`), preload `forkChat`을 추가했다.
- 새 채팅은 원본과 같은 프로젝트의 idle 상태이며 작업 폴더를 원본과 공유한다. 모델·추론·`approvalModeOverride`는 유지하고, native 세션, 작업자, 협의, 목표, 대기 승인, 승인 허용 기록은 복제하지 않는다.
- 기준 메시지는 메인 타임라인의 사용자 메시지와 마스터의 일반 답변만 허용하고, 그 외는 400을 돌려준다(`src/main/chat-fork.ts`). 화면 버튼도 같은 기준이다(`lib/fork.ts`의 `forkEventId`). 스냅샷은 사용자 메시지, 작업자·마스터 답변, 협의 요청과 결과, 동료 메시지, 질문·답변만 담는다. 도구·승인·알림은 제외하고 작성자 닉네임은 스냅샷에 보존한다.
- 첨부를 포함하면 `attachments/<새 채팅 id>/`에 독립 복사하고 새 레코드로 등록한다. 제외하면 첨부 개수만 남긴다.
- 채팅 생성·복사·이벤트 기록은 하나의 동기 savepoint에서 처리한다. 실패하면 채팅과 레코드가 남지 않고 이번 시도에서 복사한 파일을 지운다.
- 스냅샷은 대화 맥락이 없는 새 native 세션의 첫 입력에 넣는다. 계열 전환, 계정 전환, API 드라이버의 모델별 컨텍스트에도 적용된다. "지금 새로 실행하라는 지시가 아님" 경계를 함께 넣고, 스냅샷은 승인 판단기의 지시 문구에 포함하지 않는다.
- 파일 복원, Git branch, worktree 생성이 아니다.
- 원격 경로는 3개 옵션만 받고, 복사량 200MB 초과 또는 디스크 여유 부족 시 507을 돌려준다. 첨부의 로컬 경로는 기존 `stripLocalPaths`로 제거된다.

### 테스트 중 실제 Codex 기동(2026-11-09 14:13)
