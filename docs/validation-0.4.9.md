# 0.4.9 긴 대화 중 화면 프리징 개선 검증

검증일: 2026-10-16. 기준 커밋: `2ff47af`.

## 원인과 수정

실행 중인 앱의 메인 프로세스와 SQLite 기록은 계속 진행됐지만 채팅 렌더러는 높은 CPU 사용량을 보였습니다. 읽기 전용으로 확인한 약 6,900개 이벤트의 실제 대화에서, 기존 `buildItems`는 토큰이 추가될 때마다 전체 기록을 다시 계산했고 한 번에 약 0.7~1.7초가 걸렸습니다. 이 경로가 입력·스크롤·버튼 처리를 지연시키는 병목임을 확인했습니다. 모든 프리징의 단일 원인이라고 단정하는 스택 프로파일은 수집하지 않았습니다.

- 대화별 타임라인 계산기를 재사용하고 이벤트 객체가 같은 앞부분은 다시 계산하지 않습니다. 마지막 스트림 교체, 과거 이벤트 변경, 기록 축소, 보기 변경에는 필요한 위치부터 다시 계산합니다.
- 128개 이벤트마다 중간 상태를 보관하되 최근 64개와 초기 상태만 유지합니다. 대화 기록 자체를 잘라내지 않습니다. 이전 화면의 계산 결과를 변경하지 않도록 항목과 상태를 분리합니다.
- 변경하지 않은 메시지·협의·도구 항목의 참조를 유지하고 React 메모화를 적용했습니다.
- `text_delta`는 50ms 단위로 모아 화면 상태에 반영합니다. 승인·도구 결과·완성 메시지 등 다른 이벤트는 대기 중인 스트림과 함께 즉시 순서대로 반영합니다.

같은 실제 대화의 읽기 전용 계산 실험에서 수정 후 마지막 토큰 변경 30회의 평균은 약 2.5ms, 최대는 약 22.2ms였습니다. 처음 대화를 여는 전체 계산 비용은 여전히 있으며, 이 수치는 모델 응답 시간이나 전체 UI 지연을 뜻하지 않습니다.

## 검증 범위

UI 검증은 별도 Electron 창·임시 DB·합성 이벤트·가짜 IPC 응답을 사용했습니다. 실제 CLI/웹 모델에 작업이나 승인 명령을 보내지 않았습니다. 사용자의 실행 중인 앱을 종료하거나 새 코드로 교체하지 않았습니다. 현재 작업을 마친 후 새 포터블로 재실행해야 수정이 적용됩니다. 부하가 다른 실제 환경에서 재발하지 않는다는 보장은 하지 않습니다.

기존 `Ctrl+R` 또는 보기 메뉴의 새로 고침은 화면만 다시 불러오며 에이전트 작업을 중지하지 않습니다. 보내지 않은 입력은 초기화될 수 있고, 실행 중인 구버전에 새 코드를 적용하는 기능은 아닙니다.
