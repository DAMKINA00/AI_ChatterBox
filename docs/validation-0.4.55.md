# 0.4.55 — Codex 프로젝트 조회 승인 차단 수정

## 원인

기존 `innerCommand`는 작은따옴표 형태의 `-Command`만 처리했습니다. Codex의 큰따옴표 PowerShell 실행 경로와 `Get-Content | Select-Object` 조회 파이프라인은 `isReadCommand`에서 쓰기 가능 명령으로 분류됐습니다. 다른 작업자의 쓰기 잠금과 충돌하면서 승인 정책을 판단하기 전에 거절됐습니다.

승인 기록에는 범위 충돌 사유가 저장돼 있었지만 Codex 드라이버는 `decline`만 반환하고 `VerdictResult.reason`을 버렸습니다. 네이티브 응답에는 사유 필드가 없어 작업자가 일반적인 `rejected by user` 오류만 받았습니다.

## 수정

- 전체 명령이 PowerShell 호출일 때만 실행 경로·따옴표를 정규화하는 공통 함수를 사용합니다.
- 명시적인 읽기 명령과 `Select-Object`, 단순 비교 형태의 `Where-Object` 조회 파이프라인을 읽기로 분류합니다. 명령 연결·쓰기 파이프라인·리다이렉션·실행식·알 수 없는 구문은 쓰기 검사를 유지합니다.
- 읽기는 다른 작업자의 수정 범위와 충돌하지 않으며 쓰기 잠금도 획득하지 않습니다. 실제 수정 충돌, 중지, 사용자·마스터의 명시적 거절과 범위 제한은 유지합니다.
- 거절 사유를 앱에 기록하고 같은 실행 중인 Codex 턴에 `turn/steer`로 전달합니다. 지난 턴의 거절은 새 턴에 전달하지 않습니다. 승인 처리 오류도 사용자 거절과 구분합니다.
- 작업자 ID·계정·네이티브 세션·DB 스키마는 변경하지 않습니다.

## 검증

- 수정 전 두 회귀 테스트에서 잘못된 읽기 분류와 쓰기 잠금 충돌을 재현했습니다.
- 실제 거절 기록의 조회 명령 7개가 수정 후 읽기로 분류되는 것을 확인했습니다. 해당 명령을 사용자 프로젝트에서 다시 실행하지는 않았습니다.
- Codex 드라이버 → 실제 ApprovalService → Orchestrator 범위 검사 통합 테스트에서 동시 조회는 `accept`, 쓰기가 섞인 요청은 `decline`으로 반환되고 사유가 동일한 턴에 전달되는 것을 확인했습니다.
